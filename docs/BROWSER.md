# Live Flow-in-the-browser experiment

This site runs this repository's **actual Flow model** in WebAssembly. The UI is
JavaScript, but all normalization, PCA whitening, convolutions, gradients,
losses, SGD optimization, EMA updates, and inference are performed by the
original Flow entrypoints, not a JavaScript model or remote training API.

Site after deployment: https://godofecht.github.io/hlb-cifar-flow/

## Architecture

The HTML and JavaScript files in web/ render real CIFAR-10 images and metrics.
A dedicated Web Worker loads Flow WASM generated by the Flow-to-C compiler
and Emscripten, mounts a binary dataset in the Emscripten virtual filesystem,
and executes the unmodified train.flow main function. After training, the
worker retrieves its genuine version-2 EMA checkpoint and mounts it into
a separate Flow WASM instance compiled from infer.flow. Flow itself produces
all epoch metrics and prediction labels; the UI only parses its stdout.
The optional downloadable checkpoint contains the model and train-only
normalization statistics. Stop terminates the dedicated worker.

The small C adapter in web/config.c only sets environment variables and
performs bounds checks. It contains no ML computation. No PyTorch, NumPy,
JavaScript neural network, Apple MLX, WebGPU or CUDA is involved.

## Dataset and validity

The Pages workflow fetches the official 162 MB CIFAR-10 binary archive from
the University of Toronto, verifies its MD5 against the authors' published
c32a1d4ab5d03f1284b67883e8d87530 checksum, and extracts 64 deterministically
sampled records from official data_batch_1.bin and 32 independently sampled
records from official test_batch.bin. Only these genuine small subsets are
included in the site. Synthetic CI fixtures are NEVER published as examples.

The UI supports 16/32/64 training images, 8/16/32 test images, width 2/4,
batch 2/4/8 and 1/2/3 epochs. This is a correctness-oriented smoke experiment,
not a statistically useful CIFAR-10 benchmark or a reproduction of upstream
HLB's 94% A100 result. Predictions may be close to chance because of the
tiny training set. Avoid tuning hyperparameters on the official test subset.

CIFAR-10: Krizhevsky, Nair and Hinton, University of Toronto.
Official source: https://www.cs.toronto.edu/~kriz/cifar.html

## Reproducibility

The .github/workflows/pages.yml job installs Emscripten, checks out the same
pinned Flow compiler commit as native CI, invokes Flow compile on train.flow
and infer.flow, and compiles the generated C into WebAssembly. It then runs
the test in scripts/test-browser-wasm.cjs, which *actually executes* both
WASM programs on genuine CIFAR records, validates Flow epoch output,
checkpoint serialization, eight Flow predictions and reported accuracy.

On a successful push to main, the workflow deploys the validated site.
Pull requests build/test but do not deploy. GitHub Pages must be configured in
repository Settings → Pages → Build and deployment → Source: GitHub Actions.
That administrative setting cannot be changed by the GitHub connector.

To run locally, follow the build commands in the workflow, and serve the
resulting site/ folder with an HTTP server, e.g.
python3 -m http.server 8000 --directory site
WASM fetches do not work when opening the HTML with a file:// URL.

## Limitations and future work

This is CPU-only WASM, not GPU training. Browser runtimes can be slow and
memory-constrained. The dataset is tiny and the measured accuracy is not
statistically meaningful. Full dataset training, train-only validation,
WebGPU dispatch, deeper diagnostics and browser throughput characterization
require separate work and verification. The existing docs/PARITY.md describes
the current cross-backend numerical evidence and unresolved benchmark gaps.
